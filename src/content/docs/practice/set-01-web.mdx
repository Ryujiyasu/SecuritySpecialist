## 問題文

P 社は会員制 EC サイト「P-Mart」を運営している。会員数は約 30 万人で、注文情報・氏名・住所・カード番号 (4 桁マスキング表示) を保有している。
2026 年 1 月、P 社のサイト利用者から「他人の注文履歴が表示された」という問合せが連続して入った。同社のセキュリティ担当である R 課長は調査を開始した。

### システム構成

<Mermaid code={`flowchart LR
  U[利用者ブラウザ] -->|HTTPS| LB[ロードバランサ]
  LB --> Web1[Web/AP サーバ #1]
  LB --> Web2[Web/AP サーバ #2]
  Web1 & Web2 --> DB[(注文 DB)]
  Web1 & Web2 --> Cache[(セッションストア<br/>Redis)]
  U -.外部 JS.-> CDN[公開 CDN<br/>analytics.example/v1.js]
  Web1 & Web2 -.HTML 内に script タグ.-> CDN
`} />

- 認証は ID/PW + メール OTP
- セッションは Redis に保存、Cookie 名 `PSID`、有効期限 30 分
- 注文履歴ページの URL: `https://p-mart.example/orders/{order_id}` (例: `/orders/AB123456`)
- 利用者は自分の注文一覧から個別注文ページへ遷移する
- マーケティング目的で外部の `analytics.example` から JS を読み込んでおり、解析結果を取得している

### R 課長が取得した情報

1. 注文履歴ページのアクセスログを調査したところ、利用者 X が**自分の注文一覧に表示されていない `order_id`** にアクセスした記録がある
2. アクセス時刻周辺で、**利用者 X のセッションは正規にログイン済み**だった
3. その時、X は**メール OTP を一度も入力していない** (前回ログインから 30 日以上経過していたが、セッションは別経路で延長されていた)
4. 注文履歴ページの取得処理を確認すると、`order_id` でクエリし、結果を返している。所有者チェックは行われていない
5. M 主任は「`order_id` の値はランダムな英数字なので推測されない。問題ないはずだ」と発言

#### 関連するアクセスログ抜粋

```
[2026-01-15 10:42:11] uid=X      GET /orders/CD789012  200  4.2KB  PSID=...
[2026-01-15 10:42:18] uid=X      GET /orders/CD789013  200  4.0KB  PSID=...
[2026-01-15 10:42:24] uid=X      GET /orders/CD789014  200  3.8KB  PSID=...
[2026-01-15 10:42:30] uid=X      GET /orders/CD789015  200  4.1KB  PSID=...
```

### 並行して発覚した別事象

サイト利用者の数名から「ログイン後に**フィッシングと思われるポップアップ**が表示された」という申告。
調査により、外部 CDN `analytics.example/v1.js` が**改ざん**され、悪意のあるコードが含まれていた。
その JS は P-Mart の HTML から `<script src="https://analytics.example/v1.js"></script>` で読み込まれていた。

## 模範解答

### 設問 1 模範解答

<details class="sc-answer">
<summary>解答例</summary>

**解答 (65 字):**
> サーバが注文取得時に `order_id` の所有者と認証済み利用者の一致を検証していないため、他人の注文も取得できる。

**採点ポイント:**
- 「**所有者と認証済み利用者の一致検証なし**」が必須キーワード
- 「アクセス制御 / 認可の不備」のいずれかの用語を含めると更に良い
- OWASP Top 10 の **A01:2021 Broken Access Control / IDOR** に該当

**よくある誤答:**
- 「セッション管理の不備」(本問はセッションは正常、認可がない)
- 「`order_id` が推測されたため」(設問 3 で扱う論点と混同)
</details>

### 設問 2 模範解答

<details class="sc-answer">
<summary>解答例</summary>

**解答 (75 字):**
> 注文取得処理で、サーバが `order_id` の所有者をセッションに紐づく利用者 ID と照合し、不一致なら HTTP 403 を返す処理を追加する。

**採点ポイント:**
- 「**サーバ側で**」明記 (クライアント側の制御では無意味)
- 「**所有者と利用者 ID を照合**」という具体処理
- 不一致時の挙動 (403/エラーを返す) を含めると満点

**よくある誤答:**
- 「`order_id` を予測不可能にする」(対策にならない)
- 「OTP を再要求する」(認可ではなく認証の話にすり替えている)
</details>

### 設問 3 模範解答

<details class="sc-answer">
<summary>解答例</summary>

**解答 (55 字):**
> 自分の注文一覧から把握した `order_id` 周辺を順に試すなど、推測ではなく**列挙**で他人の ID を発見できるため。

**採点ポイント:**
- 「**列挙 / 探索**」または「自分の `order_id` を起点に試行」を明示
- ログの時刻が連続していることから、**自動化された総当たり**を読み取る視点
- 「ランダムなら安全」という前提が**漸進的に近接した値ならヒット**することで崩れる
</details>

### 設問 4 模範解答

<details class="sc-answer">
<summary>解答例</summary>

| 仕組み | 効果 |
| --- | --- |
| **SRI (Subresource Integrity)** | `<script>` タグに `integrity="sha384-..."` を指定し、配信された JS のハッシュが一致しない場合に**ブラウザが実行を拒否**する |
| **CSP (Content Security Policy)** | `script-src` で許可するオリジンを限定し、改ざんで他オリジンから追加読込みされた場合の被害を抑える |

**採点ポイント:**
- SRI のハッシュ検証メカニズムが説明できているか
- CSP は「設定できるディレクティブの種類」ではなく**実行制限効果**を書くこと
- 「外部 JS の利用をやめる」は対策の本質ではない (本問では分析に必須という前提)

**追加で書けると良い対策:**
- CDN 提供元の **改ざん監視 (定期的なハッシュ検証バッチ)**
- **NEL / Reporting API** で改ざん発生時のテレメトリ取得
</details>

### 設問 5 模範解答

<details class="sc-answer">
<summary>解答例</summary>

**問題点 (45 字):**
> 30 日以上経過してもセッションが OTP 未経由で延長され、認証強度が形骸化していた点。

**対策 (45 字):**
> 一定期間 (例: 30 日) を超えるセッション延長時に、OTP 含む再認証を必須化する。

**採点ポイント:**
- **絶対タイムアウト** + **再認証要求** の組合せが本質
- 「セッション時間を短くする」だけでは不十分 (利用者体験との両立観点が抜ける)
- 「**ステップアップ認証**」の概念に言及できると上位答案
</details>
