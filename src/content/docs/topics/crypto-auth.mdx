### 共通鍵 vs 公開鍵: 試験で問われる比較

| 観点 | 共通鍵暗号 | 公開鍵暗号 |
| --- | --- | --- |
| 速度 | 速い (約 100 倍以上) | 遅い |
| 鍵管理 | n 人なら **n(n-1)/2 個** | n 人なら **2n 個** |
| 主な用途 | 大容量データの暗号化 | 鍵交換・電子署名 |
| 代表例 | AES-128/256, ChaCha20 | RSA-2048+, ECDSA P-256 |

<div class="sc-key">
鍵の数の公式は午前 II の頻出問題。「100 人の組織で全員と通信するなら共通鍵は何個必要か」=
**100 × 99 / 2 = 4,950 個**。
</div>

## TLS 1.3 ハンドシェイク

TLS は **鍵交換 (公開鍵)** + **データ暗号化 (共通鍵)** + **完全性保証 (MAC/AEAD)** の合わせ技。
TLS 1.3 は **1-RTT** で確立する点が試験頻出。

<Mermaid code={`sequenceDiagram
  autonumber
  participant C as クライアント
  participant S as サーバ
  C->>S: ClientHello<br/>(Random, KeyShare, 暗号スイート候補)
  S->>C: ServerHello<br/>(Random, KeyShare, 選択された暗号スイート)
  Note over C,S: 共有鍵生成 (ECDHE)
  S->>C: {Certificate}<br/>{CertificateVerify}<br/>{Finished}
  Note over C,S: ここから暗号化通信
  C->>S: {Finished}
  C->>S: {Application Data}
  S->>C: {Application Data}
`} />

<div class="sc-trap">
TLS 1.2 と 1.3 を混同しないこと。1.2 は 2-RTT、RSA 鍵交換やセッション再開 (Session ID) があり、
1.3 はこれらが廃止され、PFS (前方秘匿性) を保証する **(EC)DHE のみ** になった。
</div>

### サーバ証明書の検証で確認される項目

1. **チェーン検証**: ルート CA まで署名が辿れるか
2. **有効期限**: notBefore / notAfter
3. **ホスト名一致**: SAN (Subject Alternative Name) が要求ドメインと一致するか
4. **失効確認**: OCSP / CRL で失効していないか
5. **使用目的**: ExtendedKeyUsage に serverAuth が含まれるか

<div class="sc-trap">
午後問題で「証明書エラーの原因を答えよ」と問われたら、**この 5 項目のどれか**。
特に SAN 不一致 (CN ではなく SAN を見る点) と中間 CA の配信漏れは超頻出。
</div>

## 認証 vs 認可

| | 認証 (Authentication) | 認可 (Authorization) |
| --- | --- | --- |
| 何を確認 | 「誰か」を確認 | 「何ができるか」を確認 |
| 例 | ID/PW、生体、FIDO | ロール、ACL、スコープ |
| プロトコル | OIDC、SAML、FIDO2 | OAuth 2.0 |

<div class="sc-key">
**OAuth 2.0 は認可、OIDC (OpenID Connect) は認証**。OAuth 2.0 の上に ID Token を載せて認証機能を足したのが OIDC。
混同すると午前・午後とも一発失点。
</div>

## OIDC 認可コードフロー (PKCE 付き)

<Mermaid code={`sequenceDiagram
  autonumber
  participant U as User-Agent (Browser)
  participant RP as Relying Party<br/>(Client App)
  participant OP as OpenID Provider
  Note over RP: code_verifier 生成<br/>code_challenge = SHA256(verifier)
  U->>RP: アクセス
  RP->>U: 302 → OP /authorize<br/>(client_id, scope, redirect_uri,<br/>code_challenge, state, nonce)
  U->>OP: /authorize へ遷移
  OP->>U: ログイン画面
  U->>OP: 認証情報入力
  OP->>U: 302 → redirect_uri?code=...&state=...
  U->>RP: redirect_uri (code, state)
  RP->>OP: /token<br/>(code, code_verifier, client_secret)
  Note over OP: code_challenge と<br/>SHA256(code_verifier) を比較
  OP->>RP: id_token + access_token
  Note over RP: id_token の署名検証<br/>iss/aud/nonce/exp 確認
`} />

### PKCE が解く問題

PKCE (Proof Key for Code Exchange) は **認可コード横取り攻撃** を防ぐ。
公衆 Wi-Fi などでリダイレクトされた `code` が盗まれても、**code_verifier を知らない攻撃者は token に交換できない**。

## FIDO2 / WebAuthn

パスワードレス認証の標準。**サーバ側に秘密情報を保存しない** のが革命的。

<Mermaid code={`sequenceDiagram
  autonumber
  participant U as ユーザ
  participant B as ブラウザ
  participant A as 認証器<br/>(YubiKey/Touch ID)
  participant RP as RP サーバ
  Note over U,RP: 登録フロー
  RP->>B: challenge + RP info
  B->>A: navigator.credentials.create()
  A->>U: ユーザ確認 (PIN/指紋)
  U->>A: 同意
  A->>B: 公開鍵 + attestation
  B->>RP: 公開鍵を保存
  Note over U,RP: 認証フロー
  RP->>B: challenge
  B->>A: navigator.credentials.get()
  A->>U: ユーザ確認
  U->>A: 同意
  A->>B: 署名 (秘密鍵で challenge を署名)
  B->>RP: 署名検証 (登録済み公開鍵で)
`} />

<div class="sc-key">
FIDO2 がフィッシング耐性を持つ根拠は **RP ID (オリジン) を認証器が確認** するため。
攻撃者が偽サイトに誘導しても、認証器が偽サイトのオリジンに対する署名を作らない。
</div>

## 確認問題

<details class="sc-answer">
<summary>Q1. AES-256 で 1 GB のファイルを暗号化する場合、RSA-2048 と比べて速度差はおおよそ何倍か。</summary>

**A. 約 1,000 倍以上。**
公開鍵暗号は計算コストが大きいため、実運用では **公開鍵で共通鍵を交換 → 共通鍵で本文を暗号化**
というハイブリッド方式 (TLS もこれ) が用いられる。
</details>

<details class="sc-answer">
<summary>Q2. ある Web サイトにアクセスすると証明書エラー。原因として可能性のある事象を 3 つ挙げよ。</summary>

**A. 例:**
1. SAN がアクセスしたホスト名と一致しない
2. 有効期限切れ (notAfter を過ぎている)
3. 中間 CA 証明書をサーバが配信していない (ブラウザがチェーンを構築できない)
4. ルート CA がブラウザの信頼ストアに無い (社内 CA など)
5. OCSP/CRL で失効が報告されている
</details>

<details class="sc-answer">
<summary>Q3. OAuth 2.0 と OIDC の最大の違いを 1 行で。</summary>

**A. OAuth 2.0 はリソースアクセス**の**認可**プロトコル、**OIDC** は OAuth 2.0 上に **ID Token (JWT)** を載せた**認証**プロトコル。
</details>
