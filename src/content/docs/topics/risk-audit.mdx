### リスクの定量化 (期待損失)

リスクの大きさは概ね以下で表す。

> **期待損失 = 発生確率 × 1 件あたり損失額**

または定性的に:

> **リスクレベル = 発生可能性 × 影響度**

## リスク対応の 4 戦略

<Mermaid code={`mindmap
  root((リスク対応))
    回避
      事業から撤退
      機能を提供しない
    低減
      技術対策
      手順整備
      教育
    移転
      保険
      アウトソース
      クラウド利用
    受容
      残留リスクとして許容
      経営判断
`} />

| 対応 | 適用例 |
| --- | --- |
| **回避** | リスクの高い機能を**提供しない**、事業から撤退 |
| **低減** | FW 設置、暗号化、教育で**確率や影響を下げる** |
| **移転** | サイバー保険、保守委託、責任分担をクラウド側に |
| **受容** | 残留リスクが小さく、対応コストの方が大きいと判断 |

<div class="sc-trap">
午後の頻出パターン: 「**リスク移転** = 責任もすべて移転されるか」→ いいえ。
**説明責任 (accountability) は移転できない**。委託先の事故も、委託元が個情法上の責任を負う (24-25 条)。
</div>

## システム監査 (システム監査基準)

### 監査の独立性

<Mermaid code={`flowchart LR
  A[被監査部門<br/>業務遂行] --> X{独立した立場}
  B[監査人] --> X
  X --> R[客観的評価]
  R --> M[経営層への報告]
  C[内部監査人] -.組織内.-> X
  D[外部監査人] -.組織外.-> X
  style X fill:#fff2cc
`} />

監査の信頼性は **独立性** で担保される。監査人は被監査部門と人事的・業務的に独立。

### システム監査の手順

| フェーズ | 主な活動 |
| --- | --- |
| **計画** | 監査目的・範囲・体制・スケジュール、リスク評価 |
| **予備調査** | 業務の概要把握、システム構成、関連規程の確認 |
| **本調査** | コントロール評価、テスト実施 (ウォークスルー、サンプリング) |
| **評価・結論** | 結果の取りまとめ、結論の導出 |
| **報告** | 監査報告書、改善提案 |
| **フォローアップ** | 改善状況の確認 |

### 監査証拠の収集技法

| 技法 | 内容 |
| --- | --- |
| **ヒアリング** | 関係者への質問 |
| **査閲** | 規程・記録・ログを確認 |
| **観察** | 現場での実施状況確認 |
| **再実施** | 同じ手順を監査人が再実行 |
| **CAAT** (Computer-Assisted Audit Technique) | データ分析ツールによる検証 |

<div class="sc-key">
午後で「監査証拠として何を確認すべきか」を問われたら、**規程の存在 → 規程通りの運用 → 運用の証跡 (ログ等)** の 3 段階を挙げる。
規程があるだけ、運用しているだけでは不十分。**証跡で証明できること**が監査の本質。
</div>

## 内部統制 (J-SOX, IT 統制)

### IT 統制の階層

<Mermaid code={`flowchart TD
  A[全社的統制<br/>(Entity Level Control)] --> B[業務処理統制<br/>(Application Control)]
  A --> C[IT 全般統制<br/>(IT General Control)]
  C --> C1[システム開発・変更]
  C --> C2[アクセス管理]
  C --> C3[運用・障害対応]
  C --> C4[外部委託管理]
  B -.依存.-> C
  style A fill:#fff2cc
  style C fill:#cfe5ff
`} />

### IT 全般統制 (ITGC) で確認される論点

| 論点 | 試験頻出のチェック内容 |
| --- | --- |
| 開発・変更管理 | **本番環境への変更承認**、テスト実施、本番反映の権限分離 |
| アクセス管理 | 申請・承認、定期棚卸、退職者の即時無効化 |
| 運用管理 | ジョブスケジュール、障害対応の手順、バックアップ |
| 外部委託 | 契約・SLA、委託先評価、定期報告 |

<div class="sc-trap">
**職務分離 (Segregation of Duties)** は試験頻出。「開発者が本番デプロイの権限を持つ」「同一人物が申請と承認を兼ねる」のような構成は ITGC 上 NG。
</div>

## 監査と CSIRT・ISMS の関係

<Mermaid code={`flowchart LR
  ISMS[ISMS<br/>運用部門] -->|定期報告| MGMT[経営層]
  CSIRT[CSIRT<br/>インシデント対応] -->|インシデント報告| MGMT
  AUDIT[監査人] -->|監査報告| MGMT
  AUDIT -.独立評価.-> ISMS
  AUDIT -.独立評価.-> CSIRT
  MGMT -->|是正指示| ISMS
  MGMT -->|是正指示| CSIRT
  style AUDIT fill:#fff2cc
`} />

<div class="sc-key">
監査は **「規程通りに運用されているか」を独立した立場から確認** する役割。
ISMS や CSIRT の運用部門と独立しているからこそ客観性が保たれる。
**監査は実装作業はしない**点に注意 (発見した問題への改善は被監査部門が行う)。
</div>

## 確認問題

<details class="sc-answer">
<summary>Q1. リスクアセスメントの 3 段階を順に答えよ。</summary>

**A.** リスク**特定** → リスク**分析** → リスク**評価**。
特定で何が脅威か、分析で発生確率と影響度を見積もり、評価で受容可能か判定する。
</details>

<details class="sc-answer">
<summary>Q2. 監査人は被監査部門の改善活動を直接行ってよいか。</summary>

**A.** **行ってはいけない**。監査人が改善実装に関わると独立性が失われ、後の監査で自分の作業を評価することになる。
監査人は問題点の指摘と提案までで、実装は被監査部門の責任。
</details>

<details class="sc-answer">
<summary>Q3. 「リスクをサイバー保険に加入することで対応した」これは 4 戦略のどれに該当するか。</summary>

**A.** リスク**移転**。ただし金銭的損失の補填は移転できても、**社会的信用や個情法上の責任は移転できない**点を併せて押さえる。
</details>
