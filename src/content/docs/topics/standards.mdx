## ISMS (ISO/IEC 27001)

### PDCA サイクル

<Mermaid code={`flowchart LR
  P[Plan<br/>方針・リスク評価<br/>適用宣言書 SoA] --> D[Do<br/>運用・教育]
  D --> C[Check<br/>監視・内部監査<br/>マネジメントレビュー]
  C --> A[Act<br/>是正・継続改善]
  A --> P
`} />

### よく問われる用語

| 用語 | 意味 |
| --- | --- |
| ISMS 適用範囲 | 組織のどこまでを ISMS の対象にするか定義した範囲 |
| **適用宣言書 (SoA)** | 採用/不採用の管理策を理由付きで列挙した文書 |
| **リスクアセスメント** | 資産特定 → 脅威/脆弱性分析 → リスク評価 |
| **リスク対応** | 回避 / 低減 / 移転 / 受容 |
| 残留リスク | 対応後に残るリスク。経営判断で受容 |

<div class="sc-key">
**SoA (Statement of Applicability)** が適用宣言書。これは ISMS 認証審査で必ず確認される最重要文書。
午後で「監査で SoA を確認した目的は何か」と問われたら、
「組織が選択した管理策と、不採用とした管理策の理由を確認するため」が定型答案。
</div>

## NIST CSF (Cybersecurity Framework)

5 つのコア機能。**順序が試験頻出**。

<Mermaid code={`flowchart LR
  ID[Identify<br/>特定] --> PR[Protect<br/>防御]
  PR --> DE[Detect<br/>検知]
  DE --> RS[Respond<br/>対応]
  RS --> RC[Recover<br/>復旧]
  RC -.学習.-> ID
  style ID fill:#fff2cc
  style PR fill:#cfe5ff
  style DE fill:#dff5d8
  style RS fill:#ffe2c5
  style RC fill:#f2d8f5
`} />

| 機能 | 主な内容 |
| --- | --- |
| Identify | 資産・リスク・ガバナンスの**特定** |
| Protect | アクセス制御、教育、データ保護 |
| Detect | 異常検知、継続的監視 |
| Respond | インシデント対応、コミュニケーション |
| Recover | 事業継続、復旧計画、改善 |

<div class="sc-key">
NIST CSF 2.0 (2024) では **GOVERN** が 6 番目の機能として追加された。
「全機能を統括するガバナンス」として、戦略・役割・リスクマネジメント方針を扱う。
</div>

## NIST SP800-61 (インシデント対応ライフサイクル)

<Mermaid code={`flowchart LR
  A[1. 準備] --> B[2. 検知と分析]
  B --> C[3. 封じ込め<br/>根絶<br/>復旧]
  C --> D[4. 事後活動<br/>教訓]
  D -.改善.-> A
  C -.再発.-> B
  style C fill:#ffd6d6
`} />

### 封じ込め戦略の選択軸

| 軸 | 検討事項 |
| --- | --- |
| 証拠保全の重要度 | フォレンジックが必要なら**シャットダウンしない** |
| 業務影響 | 完全分離か段階分離か |
| 攻撃者検知のリスク | 監視継続のメリット vs 被害拡大リスク |
| 一時的 vs 恒久的 | 一時隔離 → 根絶 → 復旧の順 |

<div class="sc-trap">
午後の頻出パターン: 「**サーバを直ちにシャットダウンすべきか**」
→ メモリ上の証拠 (実行中マルウェア、揮発性レジスタ) が消えるため **メモリダンプ・ネットワーク隔離が先**。
即シャットダウンは原則 NG。
</div>

## NIST SP800-207 (ゼロトラスト)

7 つの基本原則 (要点):

1. すべての**データソースとコンピューティングサービス**はリソース
2. ネットワーク所在地に関わらず**通信は保護**
3. リソースへのアクセスは**セッション単位**で許可
4. アクセスは**動的ポリシー**で決定 (ID/端末/時刻/位置)
5. 全資産の **完全性とセキュリティ姿勢を監視**
6. 認証/認可は**動的かつ厳格**
7. **資産・通信・状態の情報を収集**し、ポリシー改善に活用

## PCI DSS (カード業界)

カード会員データ (Cardholder Data) を扱う事業者の必須基準。v4.0 では認証強化が大きい。

| カテゴリ | 例 |
| --- | --- |
| ネットワーク保護 | 1, 2 (FW, 既定値変更) |
| カード会員データ保護 | 3, 4 (保管時/伝送時の暗号化) |
| 脆弱性管理 | 5, 6 (マルウェア対策, 安全な開発) |
| アクセス制御 | 7, 8, 9 (最小権限, 多要素認証, 物理) |
| 監視 | 10, 11 (ログ, テスト) |
| ポリシー | 12 (情報セキュリティポリシー) |

<div class="sc-trap">
v4.0 (2024 全面適用) で **MFA がすべての CDE アクセスで必須**、Webアプリにも **WAF または同等のテクニカル制御** が要求される。
午後で「CDE への管理者アクセスに MFA がない」のような構成図が出たら、PCI DSS 準拠違反として指摘する。
</div>

## 確認問題

<details class="sc-answer">
<summary>Q1. ISMS の適用宣言書 (SoA) に書くべき内容を 3 つ。</summary>

**A.**
1. 採用する管理策とその理由
2. 不採用とする管理策とその理由 (除外理由)
3. 既に実装済みかどうかの状態
追加で「管理策を満たすための手順や規程の参照」も含まれる。
</details>

<details class="sc-answer">
<summary>Q2. NIST CSF の 5 機能を順に答えよ。</summary>

**A.** Identify → Protect → Detect → Respond → Recover (CSF 2.0 では GOVERN が全体統括として追加)。
</details>

<details class="sc-answer">
<summary>Q3. SP800-61 のインシデント対応で「封じ込め前にやるべきこと」とは何か。</summary>

**A.** 検知と分析 (証拠の収集、影響範囲の特定、優先度付け)。
特に**揮発性データ (メモリ、ネットワーク接続情報) の保全** を行ってから封じ込めに進む。
</details>
