## CSIRT の位置づけと体制

CSIRT (Computer Security Incident Response Team) は **インシデント発生時の専門対応チーム**。
組織内 CSIRT のほか、業界 ISAC、JPCERT/CC のような国レベル CSIRT がある。

<Mermaid code={`flowchart TD
  CISO[CISO] --> CSIRT[組織内 CSIRT]
  CSIRT --> CMD[指揮統制]
  CSIRT --> FOR[フォレンジック]
  CSIRT --> ANA[マルウェア解析]
  CSIRT --> COM[広報/コミュニケーション]
  CSIRT --> LIA[渉外/顧客対応]
  CSIRT -.連携.-> SOC[SOC<br/>常時監視]
  CSIRT -.連携.-> JPCERT[JPCERT/CC]
  CSIRT -.連携.-> ISAC[業界 ISAC]
  CSIRT -.連携.-> POL[警察]
`} />

### 試験で問われる CSIRT の機能

| 機能 | 主な内容 |
| --- | --- |
| **インシデント対応** | 検知から復旧までの一次対応 |
| **脆弱性ハンドリング** | 脆弱性情報の集約・パッチ判断 |
| **アーティファクト分析** | マルウェア検体の解析 |
| **アラート発信** | 組織内/外部への注意喚起 |
| **教育・訓練** | 演習の企画・実施 |

<div class="sc-key">
試験では「CSIRT は **検知**もする組織か」がよく問われる。CSIRT の主機能は **対応** だが、SOC を内包する組織もあるため**組織設計次第**。
NIST SP800-61 では検知も含む包括的なチームとして定義される。
</div>

## インシデント対応の標準フロー (NIST SP800-61 ベース)

<Mermaid code={`flowchart TD
  S[インシデント検知] --> T[トリアージ<br/>影響度・緊急度評価]
  T --> Q1{経営報告<br/>必要?}
  Q1 -->|Yes| ESC[エスカレーション<br/>CSIRT長/CISO]
  Q1 -->|No| INV[初動調査]
  ESC --> INV
  INV --> EVD[証拠保全<br/>メモリダンプ/ログ取得/<br/>ディスクイメージ]
  EVD --> CON[封じ込め<br/>ネットワーク隔離/アカウント停止]
  CON --> ERA[根絶<br/>マルウェア除去/<br/>パッチ適用/設定変更]
  ERA --> REC[復旧<br/>業務再開]
  REC --> POST[事後分析<br/>RCA/再発防止]
  POST -.学習.-> S
`} />

### 封じ込めの方針 (試験頻出)

> 即座にシャットダウンするか、監視継続するか

| 観点 | 即シャットダウン | 監視継続 |
| --- | --- | --- |
| 被害拡大 | **最小化** | 拡大リスクあり |
| 証拠保全 | 揮発性データ消失 | **保全しやすい** |
| 攻撃者の戦術把握 | 不可 | 可能 |
| 業務影響 | 大 | 制御可能 |

<div class="sc-trap">
午後問題で「サーバを直ちに停止すべきか」と問われたら、**揮発性データの保全** を優先する立場で答える。
具体的には:
1. **メモリダンプ** (Volatility 等で解析)
2. **ネットワーク接続情報の取得** (`netstat`, ファイアウォールログ)
3. **稼働プロセス情報の取得**
4. その後にネットワーク**隔離** (シャットダウンではなく)
</div>

## デジタルフォレンジックの基本

### 証拠の取扱原則 (Chain of Custody)

<Mermaid code={`flowchart LR
  A[証拠採取<br/>誰が/いつ/どこで] --> B[ハッシュ計算<br/>SHA-256]
  B --> C[保管<br/>封印・施錠]
  C --> D[移送<br/>移動記録]
  D --> E[解析<br/>コピーで実施]
  E --> F[再ハッシュ確認<br/>同一性証明]
  style B fill:#cfe5ff
  style F fill:#cfe5ff
`} />

<div class="sc-key">
**証拠の同一性は SHA-256 等のハッシュ値**で示す。採取時 → 解析時 → 法廷提出時、各段階でハッシュが一致することを示せれば、改ざんがないことの証拠になる。
原本は保管し、解析は **必ずビット単位の複製 (forensic image)** に対して行う。
</div>

### 揮発性データの優先順位 (RFC 3227)

1. レジスタ・キャッシュ
2. ARP テーブル・ルーティング/プロセス情報
3. **メモリ (RAM)**
4. **一時ファイル**
5. ディスク
6. リモートログ
7. 物理構成・ネットワークトポロジ
8. 媒体上のデータ

## 脆弱性ハンドリングと CVD

CVD (Coordinated Vulnerability Disclosure) は脆弱性発見者と開発者・JPCERT/CC が**協調して開示** するプロセス。

<Mermaid code={`sequenceDiagram
  autonumber
  participant 発見者
  participant IPA as IPA<br/>(届出受付)
  participant JPCERT as JPCERT/CC<br/>(調整)
  participant 開発者
  発見者->>IPA: 脆弱性届出
  IPA->>JPCERT: 受付通知
  JPCERT->>開発者: 連絡
  開発者->>JPCERT: 確認・修正計画
  JPCERT->>発見者: 進捗共有
  Note over 発見者,開発者: 修正完了
  JPCERT->>JPCERT: JVN 公表
  JPCERT->>発見者: 公表通知
  JPCERT->>開発者: 公表通知
`} />

<div class="sc-key">
情報処理推進機構 (IPA) と JPCERT/CC は届出経路で連携。
**届出は IPA、調整は JPCERT/CC、公表は JVN (Japan Vulnerability Notes)** が役割分担。
</div>

## 危機管理コミュニケーション

### 通知すべきステークホルダー

| 相手 | タイミング | 通知すべき内容 |
| --- | --- | --- |
| 経営層 | 即時 | 影響範囲・対応方針・支援要請 |
| **個人情報保護委員会** | 速報 3-5 日 / 確報 30 日 | 漏えい等の報告 |
| 本人 | 速やかに | 漏えいした項目・原因・対応 |
| 警察 | 必要に応じ | 不正アクセス禁止法等の被害届 |
| 金融庁/監督官庁 | 業法による | 業界規制に基づく報告 |
| **JPCERT/CC** | 任意 | 攻撃情報の共有 |
| 報道 | 適切なタイミング | プレスリリース |

<div class="sc-trap">
**第一報の出し方** が試験で問われる。「事実として確認できたこと」「現在進行中の対応」「再発防止に向けた取り組み」を分け、
**推測や未確認情報は明示せず**、続報のタイミングを示すのが定石。
</div>

## 訓練 (BCP/DR と兼ねて)

| 訓練種別 | 内容 | 頻度 |
| --- | --- | --- |
| 机上訓練 (TTX) | シナリオを基に対応手順を読み合わせ | 半期 |
| **ウォークスルー** | 各役割が手順を実演 | 半期 |
| **シミュレーション** | 模擬攻撃を発生させ実際に対応 | 年次 |
| **レッドチーム演習** | 本物の攻撃者役 vs 防御チーム | 年次 |

<div class="sc-key">
試験で「インシデント対応の実効性を高める方法」と問われたら、**訓練の繰り返しと教訓のフィードバック** が定型答案。
机上訓練 → 実演 → レッドチーム、と段階を上げる。
</div>

## 確認問題

<details class="sc-answer">
<summary>Q1. メモリダンプを取得するべき理由を 1 行で。</summary>

**A.** メモリ上にしか存在しない**揮発性データ** (実行中プロセス、暗号鍵、ネットワーク接続、未保存ペイロード等) を**シャットダウン前に保全** するため。
</details>

<details class="sc-answer">
<summary>Q2. JPCERT/CC への報告は法的義務か。</summary>

**A.** 法的義務ではない (一部重要インフラを除く)。**任意の情報共有先**だが、業界横断的な攻撃情報集約のため、**できるだけ報告するのが望ましい**。
</details>

<details class="sc-answer">
<summary>Q3. インシデント対応の事後分析で必ず行うべきことを 2 つ。</summary>

**A.**
1. **根本原因分析 (RCA)**: なぜ防げなかったか、検知が遅れた理由
2. **再発防止策の策定とフィードバック**: 手順・教育・技術対策への反映、SoA の更新
</details>
